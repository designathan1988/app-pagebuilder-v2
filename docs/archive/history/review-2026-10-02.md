### R2 — FIXED e97659b — a flaky test was seen and only re-run
- Where: app-menu spec, "pointer crossing another menu before clicking the item" (failed once in
  `e2e-affected-j2`, passed 5/5 on re-run).
- What is wrong: a test that fails once is a real signal (QA-LOG #26 is the same hover-switch delay). Re-running
  until green hides it.
- What to do: do not change the test. Find why the 150 ms hover switch fired (machine load during the affected run
  is a hypothesis to prove, not assume), fix the cause or record it with evidence in `.memory/builder.md` under
  "Known flaky", and re-check it in the stage-1 closing run.
- **Reviewer update 16:20 — root cause, it is not flaky, it is a bug:** `src/editor/input/pointer.ts:1504-1510`
  starts the `menus.hoverSwitch` timer when the pointer **enters** a menu button and never restarts it while the
  pointer keeps **moving** inside that button. The spec (`spec/BEHAVIOUR.md#app-menu`, the hover-switch item) says
  the switch waits until the pointer **rests** on the other button for 150 ms. So any crossing that spends more
  than 150 ms over Edit opens Edit even though the pointer never stopped: your traces measured 87.6–117.8 ms for
  the crossing, so a slower machine moment (the parallel affected run) or a slower person (a diagonal path over a
  ~40 px button easily takes more than 150 ms) crosses the line. That is exactly the QA-LOG #26 failure (Undo run
  instead of Save project), still reachable.
- In short: the test caught a real mismatch between the code and the spec, not machine noise; recording it as
  known flaky leaves the QA-LOG #26 failure reachable. The way to fix and prove it is yours.

- Disposition (definitive user order): defer cost optimization; safety is retained. The 209/261 (80%) measurement is accepted, not disputed as a fact. Revisit only if test execution time is the measured product bottleneck. Exploration exists only in .cache/logs/r4-exploration.*; no selector changes were integrated.
