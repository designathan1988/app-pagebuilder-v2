# The complete plan: everything Journey 03 found + everything asked in this conversation

Written on 2026-10-01, on the app at commit `4a90703`. Portuguese in the plan; code, docs and commits in English (the
project's rule). Every acronym is explained in the glossary right below (the user's request).

## Context

Journey 03 (a usability study with 3 personas, `jornada03/REPORT.md`) showed that the Builder does the job, but the
path does not inspire confidence: silent failures, shortcuts that fire on their own, squeezed fields, stuck panels, an
export with CSS 5× larger than the hand-written one, missing capabilities (global colour, shared header, data, preview
for the client). During planning the user added demands that enter **this same round**, all of them **complete**
(never "the minimum to say we have it"):

1. Fix 100 % of the Journey 03 findings (J1–J28, the 17 hypotheses, the gaps per task, the 32 wishes, the bets A–F,
   the backlog).
2. Complete interactions (every trigger and action that exists) and working behaviours.
3. Forms with masks and validation, the complete catalogue.
4. Animation working and the Timeline becoming a real timeline.
5. The visual layout tool (Layout Composer / Spatial Layout Compiler), the whole specification, as an isolated and
   removable module.
6. Look at the interface for real, panel by panel (quick panel, Style, Settings, Interactions, Insert, Layers, Styles,
   toolbar…), find what is bad and fix it; fields that look like a professional application: typing values,
   adjustment arrows (steppers), ready-made values with a preview (colours, effects, thicknesses), smart input.
7. The interface **equal to the canonical layout** (`design/final/index.html`), looked at for real.
8. Open any web address and have the page appear on the canvas equal to the original, with everything editable.
9. Commit and push to the new repository `https://github.com/designathan1988/app-pagebuilder-v2.git`, always.
10. A module that saves the site as an application for Android, Apple, Windows or a site, packaged and working.
11. Reports always with the acronyms explained.
12. From the start of the conversation: what is missing for production (CI, versions, splitting the JS bundle,
    performance tests, autosave in a single record, migrations, error telemetry, CSP, security review, user
    documentation, the state of PROJECT.md). The user said CI could come later; it enters at the end of this round.

Expected result: the app leaves the state of Journey 03 with each finding fixed and proven, and with the new features
whole, proven by real gestures in Chrome, and measured again in a Journey 04 with the same metrics.

## Rules of this round (they hold for every stage)

- **Complete or it does not count.** No stub, placeholder, TODO, "initial version". A feature closes only when it
  covers the whole domain listed here, with a scenario in the manifest, a spec in `spec/BEHAVIOUR.md`, a unit test and
  an e2e test with a real gesture.
- **Look for real, always.** Each stage ends with photos of every surface it touched, side by side with the canonical
  in the same states (light/dark, en/pt-BR), and the list of differences measured by a script; a difference becomes a
  fix before the stage closes. Never validate only by the absence of errors in the console.
- **Contract first:** a change of behaviour starts in the manifest and the spec, in the same commit as the code; one
  owner per concept (the inventory says who); no second implementation of something that already has an owner.
- **Never loosen a test.** A test or scenario changed on purpose goes in the same commit, with the spec's line and the
  reason.
- **One commit per change**, through the gate, with a QA-LOG entry (what the person saw, what changed, the hash), push
  to the v2 repository. `.memory/builder.md` rewritten after every commit.
- **End of each stage:** the e2e tests of what the stage built (`npm run e2e -- <specs>`), the photos compared, and the
  Journey 03 meter redone on the tasks the stage affects. The complete suite runs at the end of stages 5, 11 and 17.
- Reports and messages to the user in plain Portuguese, acronyms explained.

## Stage 11 — The visual layout tool (Layout Composer), the whole specification

An isolated and removable module in `src/modules/layout-composer/` (folders geometry, topology, intent, gestures,
constraints, compiler, responsive, ui, adapters, `index.ts`), one registration point in `src/app/`, its own manifest
(`manifest/features/19-layout-composer.json`, `manifest/commands/layout-composer.json`). Rules: "Freeform is an
authoring mechanism, not the runtime layout model"; layout intelligence has one owner; the result is the document's
normal structure (div/section with grid/flex) made by the owners that already exist (`core/style/tracks.ts`,
`grid-item.ts`, `set.ts`, wraps), one undo step per operation; geometry and snapping reuse `src/core/geometry/*` and
`src/editor/canvas/{coordinates,rulers,guides,snapping}` (extended, never duplicated).

The order of construction (each layer becomes real infrastructure of the next, without a skeleton):

1. One geometric engine and coordinate system (zoom, pan, DPR; precision without accumulated error).
2. Topology (regions, shared boundaries, vertices, adjacency, containment).
3. The Layout Intent Graph (geometry, topology, constraints, relations, patterns, semantics, responsive, provenance).
4. The gesture algebra (draw, split, cut, merge, merge by sweep, subtract, move, nest, detach, extract, duplicate,
   align, distribute, repeat, reshape, delete, restore) with an inverse operation; compound gestures.
5. Constraints and the solver (same width, equal gap, proportion, fill, min/max, fixed, fluid, hug).
6. A stable and minimal compiler (guillotine → nested flex; the rest → grid with areas; absolute only when an overlap
   is asked for; a cost function; provenance per node, an optional field in the document, ignored by the export).
7. The responsive continuum and morphing (on top of Stage 2).
8. Content pressure, the ambiguity engine (candidates with confidence, toggle before confirming) and the predictor
   ("3 equal columns · gap 24 · fluid").
9. Topological editing (drag a boundary, erase a boundary = merge, vertex) and structural handles by type.
10. Rulers, guides, smart guides, overlaid grids and measures in the mode (on top of what exists).
11. Pattern recognition and Repeat; refactoring of existing layouts by gesture; canonicalisation.
12. Lenses (spatial, structure, constraints, responsive, flow, semantics); constraint painting on the canvas.
13. Spatial components, layout variables, layout templates, the intent inspector.
14. Layout stress test and structural suggestions.
15. Structural import (HTML/CSS → LIG, with "recovered intent: N %") and layout diff.
16. A reference image underneath to trace (bet F).

Validation: the specification's 12 mandatory cases (header+sidebar+content, a panel with 6+ regions, asymmetric, a
repeated grid, nested, multiple split, multiple merge, subtract, structural resize, desktop→phone, real content,
reopen) with real gestures in Chrome, photos before/during/after, inspection of the DOM and of the generated CSS; a
removal test (a build without the module passes `check:fast` and the suite); performance ≤ 16 ms per pointer move.
